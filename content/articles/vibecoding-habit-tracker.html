Project: commit/

vibecoding a habit-tracking app

 20 May '26

I started using GitHub properly almost a year ago when I was trying to build the first version of my website.

It was an overengineered monstrosity.

But I was surprised by how much I enjoyed looking at my commit numbers, and seeing the heatmap fill up with little green squares. I made a habit of pushing something daily, even if it was janky. Eventually the website was built, but the idea of "at least one commit a day" stuck.

I've tried many a habit-tracking app, and it's satisfying to see lists being checked off. But they always felt flat, atomic, and reactive rather than a proactive plan for the future. Lists were something you pulled out when a deadline loomed, not when you were looking at a 5 year plan.

That was until August Bradley's PPV system (Pillars, Pipelines, Vaults), less an app and more of a "Life OS". He uses Notion to build a dynamic system that flows between abstract, lifelong goals and the practical minutia of daily tasks. Each task ladders up into their respective projects, goal outcomes, value goals and pillars i.e. the foundations of your life. That way you execute towards your important long-term goals, while course-correcting with regular review cycles. I loved the idea of looking at your life as a holistic system.

But, it never stuck for me. It was much easier to put off reviews, kick the task can down the road, and stare at my ever-growing "some-day" bucket list. Today I use a simplified and scaled down version of PPV. But I wanted to see if I could combine GitHub and PPV into a single system.

Hence "commit/", a habit-tracking app that brings together the motivation of keeping GitHub streaks alive via heatmaps while maintaining Bradley's comprehensive life design philosophy.

Design Decisions

Three themes drove my design decisions

  1. Honest self-accounting
  2. Intentional friction
  3. Emergent design

Honest self-accounting

The temptation to kick tasks down the road was one of the biggest things that made traditional habit-tracking methods ineffective for me. I could scribble out today's goal and add it tomorrow on a whim, or it would sit collecting dust if it wasn't urgent. There were three ways I tried to solve for this:

1/ GitHub Heatmaps

Streaks are not unfamiliar to the avid habit-tracking app user. GitHub's heatmap offers immediate feedback both for tasks done (or not), and higher commit activity. However, it doesn't have an ability to filter for project-specific commits, presumably because it's optimising for other complex features. Conversely, Notion doesn't have a native heatmap feature but it can drill into minute specifics of your projects (there is a similar GitHub feature implemented by a community member though https://www.reddit.com/r/Notion/comments/1pjrczh/someone_asked_a_few_weeks_ago_if_a_githubstyle/).

Bringing this to commit/, I included both a local (project-specific) and global (all projects) as an overview. In this way, the user can see a visual indicator of their current progress on two different levels.

2/ Immutable Commits

Given the decentralised nature of GitHub i.e. anyone can contribute to projects at any time from anywhere, commits and commit hashes arose from ensuring data security and that the data wasn't tampered with. The public can interrogate and view the before and after of a piece of code to ensure accountability. Sure you can revert it, but that action is recorded too.

When this lens of permanence and timestamped behaviour is translated to tasks, it changes your relationship to an object. In Notion, I could easily toggle a task on or off, unable to see that this seemingly small change had an impact on overall activity.

This was a useful feature to bring to commit/, enabling a user to view the contribution graph at both the local and global heatmap levels.

3/ In-built reviews

Although reviews are the compass for correction, it can be difficult to carve out the time to reflect. Not only that but it's challenging to set up systems for adequate data capture, compilation and analysis. There was a period of time where I faithfully tracked my time on every project I was doing, but it was only the occasional review that gave me insight into where exactly it went.

To encourage this, a short summary of stats is autogenerated in each daily, weekly, monthly, quarterly and yearly cell. It the user is unable to review the more comprehensive stat screen, a quick journal entry will hopefully be more accessible

Intentional Friction

Many habit-tracking apps have flexibility - the ability to freely toggle tasks as done or note, or start a project (but never finishing it). Therefore introducing friction intentionally was a key decision.

1/ Unidirectional Assignment

To avoid facilitating trigger-happy creations, a user can only add new items further up the chain rather than in the same level.

2/ Active Projects must have due dates

A project can only be activated if it has a due date, otherwise it will be left as backlog. Making a project active is therefore a decision to commit to completing it.

3/ Avoiding unnecessary friction

However, friction should only be added where it's helpful rather than a hinderance. I had Initially required the user to go back to projects page to select a task but found that was too much friction that it was annoying.

Emergent Design Decisions

There were a few emergent design choices that added to the experience:

1) Colour Palette

GitHub already has a recognisable colour palette. I wanted to preserve the minimal concept and if there were new colours, each would be quickly scannable:

  • Scheduled tasks (purple) = these appear in both the project local and global heatmap so upcoming events are visible and easily accessed
  • Recurring daily tasks (deep blue) = This indicates which tasks are recurring.
  • Late tasks (light blue) = If a user makes commits past their self-appointed due date, the colour changes from green to blue. The deepening colour schematic also does not appear for late entries. The app doesn't punish the user by blocking them from making commits, but it doesn't have the same subtle reward loop either.

The colour scheme was also flipped for journal entries i.e. the earlier the user submitted their reflection, the deeper the colour whereas the later they were the lighter the colour.

2) Renaming "Projects" to "Repos"

During testing I discovered that "monthly calls with friend" wasn't really a project to be completed. August Bradley also notes that sometimes projects are to be maintained but not necessarily completed. Instead, I used the broader term of "repos" to indicate that these are domains that can either be a project or an area of life.

Claude Collaboration

There were interesting points in the journey where Claude would push back on things I'd suggested. The more memorable ones were:

1) Review Reminders Given how important I considered completing reviews, I had initially thought of 3 layers of review reminders. The user would be able to configure these in Settings:

  • Remind Once = A banner would drop from the top. When viewed once it disappears.
  • Persistent Reminder = The banner remains until the user writes a review.
  • Screen Overlay = The entire stat screen gets blurred until the user writes a review.

Originally considered a full overlay but it asked me to look at a persistent but dismissable banner instead. The former was a blocker and withholding information while the latter was an invitation that respected autonomy while keeping the reminder visible. Suggested late entries are allowed but reflected late to mark them honestly. What they would hard block is editing a weekly review after submitted. "Write it late if you must, but once it's written it's immutable. That's the accountability lever that actually matters."

Your instinct is philosophically consistent with the commit model — and I think it's right— but the implementation detail matters enormously. The risk isn't that people will cheat. It's that life genuinely gets in the way... If the app hard-blocks them, the most likely outcome isn't that they write it on time next week — it's that they feel the app is punishing them and disengage".

2) Scheduled Tasks

My vision of a scheduled task is that it would appear as a purple filled cell rather than green. However I hadn't specified it in my prompt. When Claude coded it, it appeared as a small dot in the bottom right-hand corner of the cell. I hadn't considered such an elegant solution. A full purple square would've unnecessarily drawn the eye. As a dot, it was visible enough to attract attention, but not so loud that it overwhelmed the original colour palette.

3) Stat Screen

  • Asking for help on stats - Immediate visual feedback increases habit adherence by approximately 30% compared to delayed outcome tracking. The brain learns faster when cause and effect are tightly linked. Graphs allow you to concretely track progress over days and see how far you've come. By simply being aware of your performance trend, you'll have far more motivation to make even the tiniest of progress.
    • over-tracking can backfire — fueling anxiety, obsession, and perfectionism.
    • So the research points to charts, but what kind of chart matters enormously. Line graphs showing improvement over time, bar charts comparing periods, and scatter plots tracking multiple variables appeal to analytical thinkers who want to understand trends and relationships — showing improvement trajectories, not just current state.
    • They don't want to feel good — they want to understand. The chart should prompt insight, not emotion.
  • Time horizons
    • Weekly → Did I do the behaviours? (execution accountability) -- Weekly self-monitoring was found to be nearly as effective as daily tracking for established habits, with significantly lower dropout rates. weekly is the primary accountability cadence — it's where behaviour is close enough in time to still be actionable and adjustable.
    • Monthly** → Are the patterns healthy? (consistency analysis) = monthly reviews are considered essential - where you catch "tracking drift," the phenomenon where you keep recording but stop learning from the data. Monthly is the pattern-recognition layer.
    • Quarterly → Is this project actually moving? (milestone progress) = Quarterly is where the research aligns with PPV thinking — it's long enough to see genuine trend lines, short enough to course-correct within a year. Quarterly planning geared toward growth and productivity is a distinct layer from weekly and monthly
    • Yearly** → Does my commit history reflect who I'm trying to become? (identity audit) = Yearly is identity-level. Not "did I go to the gym this week" but "am I someone who trains consistently."
    • Each dashboard should ask a different question, not just show the same data at different zoom levels:
    • For habit tasks specifically, the weekly and monthly views will be most useful. Quarterly and yearly matter more for project-level metrics.

Critiques

There's a bit of lag whereas in GitHub, you're only allowed to push to your remote repo when you have done the work AND that work can be investigated by the public if you have a public repo so people can see if you've done trash commits.

What this app is NOT: Everything. The scope only contains actually executional pieces of work: pillars, projects, milestones and tasks. Making new features for the value goals and goal outcomes felt too abstract. Whilst features such as time blocks was too granular for what was needed. Practically the ideas were too complex for what feels like an already complex app

What I learned

  1. There is a gap between building, learning and understanding. What does responsibility entail?
  2. What would I do differently next time?

I fully recognise it's quite niche. It'd need a basic understanding of Git, the vocabulary and how it works. But even fewer people might find it an appealing metaphor for life.

I enjoyed the task of pairing GitHub's granular commit system and heatmapping for execution with Bradley's project management for broader life architecture and meaning. It became a lightweight version of both.
